TorchSIG Homogeneous HDF5 Merge Plan
=====================================

The work should be split into six implementation merge requests (MRs) plus a
separate sharding investigation. TorchSIG already has completion markers,
integrity validation, batched DatasetCreator writes, and PID-aware lazy file
access for the existing Signal-oriented homogeneous format. The new work
should reuse those mechanisms rather than replacing them.

Architectural recommendation
----------------------------

Preserve HomogeneousHDF5Reader, HomogeneousHDF5Writer, and homogeneous schema
version 1 for existing Signal datasets. Introduce a separate structured,
model-ready API instead of changing read() to return different types depending
on the file contents.

MR 1 - Define the structured sample contract and schema
--------------------------------------------------------

Scope:

* Define supported sample structures: arrays/tensors, tuples/lists, and
  string-keyed mappings whose leaves are fixed-shape numeric arrays.
* Add schema objects describing field path, shape, NumPy dtype, and container
  structure.
* Infer a schema from the first sample or batch.
* Validate subsequent samples against that schema.
* Reject object dtypes, variable shapes, inconsistent keys/container types,
  and unsupported leaves with field-specific errors.
* Define and version the on-disk schema without changing the existing
  homogeneous version 1 format.

Likely files:

* A new schema/structure module under torchsig/utils/file_handlers/.
* Focused schema tests under tests/utils/file_handlers/.

Tests:

* Nested input/target structures.
* Complex, floating-point, integer, and boolean dtypes.
* Scalars and multidimensional tensors.
* Shape, dtype, key, and container mismatches.
* Object-valued and variable-length fields.

This MR establishes the contract used by later work and can merge without
changing existing behavior.

MR 2 - Add the structured HDF5 writer and reader
------------------------------------------------

Dependency: MR 1.

Scope:

* Add structured homogeneous reader/writer classes using one HDF5 dataset per
  schema leaf.
* Preserve field names, structure, shapes, dtypes, values, and dataset length.
* Support efficient indexed reads and contiguous batch reads.
* Store the schema, format identifier, version, length, and completion marker
  in the file.
* Validate format/version, required datasets, field shapes/dtypes, lengths,
  and completion status when opening.
* Keep the existing Signal-oriented homogeneous reader/writer compatible.

Tests:

* Exact round trips for tuple and mapping samples.
* Multiple fields and dtypes.
* Empty, malformed, incomplete, and unsupported-version files.
* Random and contiguous indexed access.
* Regression coverage for existing homogeneous version 1 files.

MR 3 - Add a public Dataset/DataLoader materialization API
----------------------------------------------------------

Dependency: MR 2.

Scope:

* Add a public function or class accepting either a PyTorch Dataset or
  DataLoader.
* Construct a DataLoader internally when given a Dataset.
* Consume already-collated batches without treating field count as batch size.
* Support batch size, workers, collate function, expected length, and progress
  reporting.
* Correctly handle the final partial batch.
* Verify that the number written matches the declared or inferred length.
* Expose structured HDF5 as a PyTorch-compatible map-style dataset.

Tests:

* Dataset and DataLoader sources.
* Batched tuple and dictionary outputs.
* Custom collate functions.
* Partial final batches.
* Iterable datasets with and without an explicit length.
* Too few or too many source samples.
* Progress enabled and disabled.

MR 4 - Add atomic creation and explicit overwrite behavior
-----------------------------------------------------------

Dependency: MR 3.

Scope:

* Materialize into a temporary sibling path.
* Mark output complete only after data and metadata are flushed and validated.
* Atomically publish the completed output.
* Make overwrite=False reject conflicting or incomplete destinations clearly.
* Make overwrite=True replace an existing output only after the new output
  succeeds.
* Clean up temporary artifacts after expected failures where safe.
* Ensure a failed run cannot make an existing valid dataset disappear.

Tests:

* Exceptions during schema inference and midway through writing.
* Existing complete and incomplete destinations.
* Both overwrite modes.
* Existing output remains readable after replacement failure.
* Temporary output is never recognized as complete.

MR 5 - Harden worker-safe lazy access and lifecycle handling
------------------------------------------------------------

Dependency: MR 2. This can proceed in parallel with MRs 3 and 4 after MR 2.

Scope:

* Apply the existing PID-aware lazy-open pattern to the structured reader.
* Ensure HDF5 handles are excluded from pickle state.
* Reopen inherited handles after fork.
* Support spawn, persistent workers, repeated epochs, and explicit close.
* Avoid sharing h5py.File or dataset objects across processes.
* Where practical, extract the existing lifecycle logic into a small shared
  internal helper without changing public APIs.

Tests:

* DataLoader operation with 0, 2, and 4 workers.
* Spawn and fork where available.
* Reader opened in the parent before worker creation.
* Persistent workers across multiple epochs.
* Shuffled access.
* Evidence that worker processes own distinct handles or PIDs.

MR 6 - Add source/output equivalence validation
------------------------------------------------

Dependencies: MRs 3 and 5.

Scope:

* Add optional post-write validation through the public materialization API.
* Support full validation and deterministic sampled validation.
* Compare container structure, field names, shapes, dtypes, and values.
* Use exact equality by default, with optional configured tolerances for
  explicitly lossy workflows.
* Produce errors identifying the sample index and field path.
* Record the validation mode and result in output metadata.

Tests:

* Successful exact validation.
* Value, dtype, shape, and structure mismatches.
* Deterministic sampled indices.
* NaN and complex-valued behavior.
* A validation failure leaves no published complete output.

MR 7 - Add documentation and performance examples
--------------------------------------------------

Dependencies: MRs 3 through 6.

Scope:

* Document the supported sample grammar and unsupported variable-sized or
  object-valued structures.
* Provide Dataset and DataLoader examples.
* Explain when to precompute deterministic transforms and when to retain
  randomized online transforms.
* Document overwrite, atomicity, validation, worker behavior, and
  compatibility or migration considerations.
* Add a benchmark comparing online deterministic transforms with materialized
  reads using zero and multiple workers.
* Report generation time, epoch throughput, and the break-even number of
  epochs rather than asserting a universal speedup.

Separate investigation - HDF5 sharding and manifests
-----------------------------------------------------

This investigation should not block the core acceptance criteria.

Deliverables:

* A short design document evaluating shard sizing, manifest format,
  global-to-local index lookup, atomic multi-file publication,
  missing/corrupt shards, shuffle behavior, worker locality, and future
  append/resume support.
* A small prototype benchmark if needed.
* A recommendation followed by a separate implementation ticket and MR only
  if sharding demonstrates a clear operational or performance benefit.

Merge order
-----------

MR 1 -> MR 2 -> MR 3 -> MR 4 -> MR 6 -> MR 7

MR 5 can begin after MR 2 and should merge before MR 6. The sharding
investigation can proceed independently once the structured schema is settled.
