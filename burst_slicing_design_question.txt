Title: Should partial time-frequency views be generated by the dataset or extracted by a transform?

Question
--------
TorchSIG would like to simulate a receiver observing only part of a larger
time-frequency environment. Components would be created on an expanded canvas,
then a smaller time and frequency viewport would be returned. Should this
behavior be integrated into dataset generation, or should an IQ-level transform
extract the viewport from an already generated scene?

This ticket is intended to compare the designs and gather requirements. It does
not select an implementation.

Desired behavior
----------------
The larger environment may contain components that are:

- Fully visible in the returned viewport.
- Truncated at the beginning or end in time.
- Visible only through a middle time interval.
- Cropped on the lower or upper frequency side.
- Visible only through a middle frequency interval.
- Entirely outside the selected viewport.

The returned IQ data and component metadata should describe only the visible
observation. Frequency cropping must modify the physical IQ signal through
mixing, filtering, and resampling rather than merely clamping metadata.

Proposal A: integrate cropping into dataset generation
------------------------------------------------------
The dataset generator would create and place components on an expanded canvas,
select a time-frequency viewport, and return the cropped scene as its normal
sample.

Possible flow::

    configure expanded canvas
        -> generate noise and complete components
        -> place components across the canvas
        -> select time-frequency viewport
        -> extract viewport and update metadata
        -> apply output transforms and labels

Pros
~~~~
- The generator controls the full scene and component-placement process.
- Placement and cropping can be optimized together to avoid unnecessary work.
- It is easier to guarantee a requested number of visible components.
- The generator can retry placement or viewport selection to avoid empty crops.
- Canvas metadata and random generation are managed in one place.
- Integer expansion and decimation may be optimized as part of generation.
- It may provide the best performance for typical synthetic training pipelines.

Cons
~~~~
- It adds significant complexity to the core dataset generator.
- It couples partial-view simulation to synthetic generation.
- It is difficult to reuse with recorded, static, or previously cached IQ data.
- Canvas and returned-viewport metadata must coexist in the dataset API.
- Existing meanings of sample rate, sample count, frequency bounds, and
  ``num_signals_min/max`` become less obvious.
- It creates greater compatibility and reproducibility risk for existing
  dataset configurations.
- Tests are more integration-heavy because placement and observation are
  intertwined.
- Extracting multiple different views from one retained scene is less natural.

Proposal B: extract the viewport with an IQ transform
-----------------------------------------------------
The dataset would generate a larger scene normally. An opt-in transform would
select the time-frequency viewport before spectrogram and label transforms.

Possible flow::

    generate expanded scene
        -> apply component/environment operations
        -> apply time-frequency crop transform
        -> apply output impairments
        -> create spectrogram and labels

Possible exploratory API::

    SceneCrop(
        num_iq_samples=262_144,
        sample_rate=10_000_000,
        crop_time=True,
        crop_frequency=True,
        time_offset=None,
        center_freq=None,
        allow_empty=False,
    )

Pros
~~~~
- It cleanly separates environment generation from receiver observation.
- It is reusable with generated, recorded, static, and cached IQ data.
- Existing dataset behavior remains unchanged when the transform is absent.
- Time-only, frequency-only, and combined cropping can share one interface.
- Crop behavior and metadata intersection can be tested independently.
- Deterministic crop parameters can make failures easier to reproduce.
- Multiple viewports can be extracted from one retained environment.
- It composes naturally before spectrogram and label transforms.
- It creates a clear semantic boundary between canvas coordinates and returned
  viewport coordinates.

Cons
~~~~
- The input dataset must still be configured to generate a larger canvas.
- A large environment may be generated and processed only to be discarded.
- Frequency cropping requires mixing, anti-alias filtering, and resampling.
- Arbitrary input/output sample-rate ratios add implementation complexity.
- Visible-component count guarantees require crop retries or acceptance rules.
- Retained components must inherit viewport metadata rather than stale canvas
  metadata.
- Component IQ data must receive transformations consistent with the parent
  scene.
- Random iterable datasets do not automatically retain a scene for extracting
  multiple views.
- Transform ordering relative to channel and receiver impairments must be
  defined carefully.

Shared technical requirements
-----------------------------
Either design needs to define and test:

1. Time intersection for component intervals and IQ data.
2. Frequency intersection for occupied component bands.
3. Subband mixing, anti-alias filtering, and resampling.
4. Component removal when there is no visible intersection.
5. Visible ``start_in_samples``, ``duration_in_samples``, ``center_freq``, and
   ``bandwidth`` metadata.
6. Parent/component data consistency after extraction.
7. Re-parenting or local overrides for output sample rate, sample count, and
   frequency bounds.
8. SNR and bandwidth measurement before versus after cropping.
9. Label behavior for partially visible components.
10. Deterministic seeding across workers.
11. Empty-view and minimum-visible-fraction policies.
12. Performance with cropping disabled and enabled.

Questions to resolve
--------------------
- Does ``num_signals_min/max`` describe the full environment or visible view?
- Must every returned viewport contain a component?
- Should partially visible components retain their original class label?
- Should minimum visible time and bandwidth fractions be configurable?
- Are time and frequency expansion expressed as multipliers or explicit canvas
  dimensions?
- Must arbitrary sample-rate ratios be supported, or are integer factors enough
  initially?
- Which impairments represent the environment and happen before cropping?
- Which impairments represent the receiver and happen after cropping?
- Should the original unobserved component extent be retained as provenance?
- Is the feature required for IQ output, spectrogram output, or both?
- Do users need multiple deterministic views from the same stored environment?

Evidence that would support a decision
--------------------------------------
- A small transform prototype demonstrating correct IQ and metadata behavior.
- Benchmarks comparing the expanded generator and transform pipelines.
- Example visualizations of full and partially visible components.
- Feedback on recorded/static-dataset use cases.
- Measurements of how often random crops are empty or fail visibility rules.
- An assessment of metadata inheritance and serialized-format implications.

Possible outcomes
-----------------
- Implement the behavior entirely in dataset generation.
- Implement it as an IQ-level transform.
- Expose a transform API first, then optimize synthetic generation internally
  while preserving the same observable semantics.
- Provide separate generator-integrated and transform implementations for
  different use cases.
- Defer frequency cropping and initially support only time-domain burst slicing.

Next exploratory step
---------------------
Draft a minimal IQ-level transform prototype to validate time-frequency
intersection, subband extraction, metadata updates, and pipeline ordering. The
prototype should gather evidence for this design question and should not be
treated as a commitment to Proposal B.
