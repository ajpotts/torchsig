Title: Correct sampling-clock offset and jitter semantics

Problem

The existing clock engine accumulates random drift and jitter into one phase
state, so ClockDrift does not represent a fixed rate offset and ClockJitter does
not represent independent aperture jitter. The NumPy and Numba paths also use
different random-number and position-update mechanics.

Scope

- Define drift_ppm as a signed fixed sampling-rate offset.
- Apply jitter independently to each sampling instant without accumulation.
- Scale jitter in millionths of one input-sample period.
- Use absolute nominal positions and clamp jittered reads to valid boundaries.
- Keep NumPy and Numba behavior deterministic and numerically equivalent.
- Preserve output length behavior and complex64 dtype.

Acceptance criteria

- Positive offset advances through input faster than zero offset.
- Negative offset advances more slowly.
- Independent jitter does not alter nominal output length.
- Identical seeds produce identical results.
- NumPy and Numba outputs agree for combined offset and jitter.
